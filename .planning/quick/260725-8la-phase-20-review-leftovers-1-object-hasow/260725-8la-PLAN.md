Apply five edits to `src/mcp/tools/recipe.ts`:

(1) **Object.hasOwn for template membership** — in `handleCreateOneClick`, replace `if (!(parsed.type in templates))` with `if (!Object.hasOwn(templates, parsed.type))`. Rationale: `in` walks the prototype chain; `Object.hasOwn` checks own-properties only. `fetchServiceTemplates` returns a parsed JSON object whose prototype could be tampered in test fixtures; own-property check is the correct semantic.

(2) **deploy.status not_triggered when instant_deploy:false** — in all three handlers (`handleCreateGitApp`, `handleCreateAppDb`, `handleCreateOneClick`), compute the deploy status from `parsed.instant_deploy`:
- `const deployStatus = parsed.instant_deploy === false ? 'not_triggered' : 'queued';`
- Replace the literal `deploy: { status: 'queued' as const }` with `deploy: { status: deployStatus }` in each `buildReadResponse` call.
- TypeScript: widen the literal — `deployStatus` is inferred as `'not_triggered' | 'queued'`; no `as const` needed. If `buildReadResponse`'s type complains, annotate `const deployStatus: 'not_triggered' | 'queued' = ...`.

(3) **create-git-app soft-ignore deploy-fail** — in `handleCreateGitApp`, change the `triggerDeploy` catch block from `rethrowGitAppApiErrorWithManifestHint(error)` to a soft-ignore:
```
} catch {
  // Soft ignore deploy queue failure per D-16 — application created successfully;
  // agent can retry via application.deploy. Parity with handleCreateAppDb.
}
```
When deploy fails, set `deployStatus` to `'not_triggered'` (deploy did not queue) instead of `'queued'`. Implement by declaring `let deployStatus: 'not_triggered' | 'queued' = parsed.instant_deploy === false ? 'not_triggered' : 'queued';` before the try, and set `deployStatus = 'not_triggered'` inside the catch. The success response still carries `application_uuid`, so the agent has what it needs to retry.

**Decision documented:** Chose soft-ignore over `COOLIFY_RECIPE_PARTIAL_FAILURE` envelope for parity with `handleCreateAppDb`'s deploy-fail path (D-16). The partial envelope is reserved for cases where the *create* itself failed mid-orchestration leaving orphaned resources (e.g., app create fails after db create). Here, the application is fully created and usable; only the deploy queue failed, which is a retryable post-create step — same shape as `create-app-db`'s soft-ignore. The `application_uuid` in the success response gives the agent the handle to retry.

(4) **detectBuildPack cwd realpath allowlist** — rewrite `detectBuildPack` to enforce the same allowlist as `service.readBoundedComposeFile` (lines 829-886 of `service.ts`). Add `realpathSync` to the `node:fs` import (already imports `readdirSync`, `statSync`). Structure:
- Resolve `root = realpathSync(process.cwd())` — on throw, rethrow as `CoolifyApiError({ code: 'COOLIFY_VALIDATION_ERROR', message: 'Cannot resolve repo_path allowlist root: ...', recoveryHints: RECOVERY_HINTS.COOLIFY_VALIDATION_ERROR })`.
- `const resolved = path.resolve(root, repoPath);` then `realPath = realpathSync(resolved)` — on throw, rethrow as `CoolifyApiError({ code: 'COOLIFY_VALIDATION_ERROR', message: 'Cannot read repo_path at ${repoPath}: ...', recoveryHints: RECOVERY_HINTS.COOLIFY_VALIDATION_ERROR })`.
- `const rootPrefix = root.endsWith(path.sep) ? root : `${root}${path.sep}`;`
- `if (realPath !== root && !realPath.startsWith(rootPrefix))` → throw `CoolifyApiError({ code: 'COOLIFY_VALIDATION_ERROR', message: 'repo_path escapes allowlisted root (' + root + ')', recoveryHints: RECOVERY_HINTS.COOLIFY_VALIDATION_ERROR })`.
- Then proceed with the existing Dockerfile / Dockerfile.* detection, but operate on `realPath` (not `repoPath`) so symlink-resolved paths are checked.
- Keep the `'dockerfile' | 'nixpacks'` return type unchanged.

Do NOT extract a shared helper into `service.ts` or a new util — scope is this plan only; the service pattern is reused by reference, not by refactor. If a future phase wants DRY extraction, that's a separate scope.
